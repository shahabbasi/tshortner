GET /{short_code}

Opening a short link

The hot path. Redis answers most requests and Postgres is read only on a cache miss. Before the 302 goes out, the @record_short_link_access decorator publishes one access event; nothing is written to Postgres while the visitor waits.

POST /urls

Creating a short link

Requests for the same URL first take a Redis lock shared by every instance, so a duplicate waits for the first request to finish and then finds its row. Codes are generated in the app, not by the database: each instance draws the first character from its own SHORT_CODE_PREFIXES, so instances given disjoint sets can never mint the same code.

2 threads per instance

Counting clicks and expiring links

Each instance runs two daemon threads with their own event loop, Redis connection, and Postgres engine; the async drivers can't share the request loop's connections. Every instance receives every access event, and its worker keeps only codes that start with its own SHORT_CODE_PREFIXES. GET /urls/{id}/stats reads click_count, so counts trail live traffic by up to one flush.

Known limits

Behaviour the current design accepts, and what would change it.

Lost clicks
Pub/sub keeps no backlog. Events published while the owning instance's worker thread is down or restarting are dropped, so click_count undercounts.
Double counting
Separate instances with disjoint prefixes count each click once. Several server processes sharing one prefix set, such as uvicorn with multiple workers, or instances with overlapping prefixes, still save the same event more than once. Run one process per instance.
Lagging stats
click_count changes once per flush, so /urls/{id}/stats can be up to 60 s behind.
